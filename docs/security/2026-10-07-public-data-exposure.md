No rows were inserted, changed, or deleted by the migration. The backup has no
client policies intentionally: it is an administrative archive, not an app table.
The live catalog is `catalogo_maestro` and remains available to signed-in users.

At source base `3e6251ba5e4f02ae92cbda21dac0e03b49f81ffb`, no frontend or runtime
reference to the backup or raw-SQL helpers was found. The three `exec_sql` source
call sites are maintenance scripts using `SUPABASE_SERVICE_KEY`.
`transition_task_status` is used by both the browser and server, so authenticated
execution was preserved.

The maintenance script `functions/scripts/executeSqlMigration.js` now prints a
transaction containing restrictive grants whenever it instructs an administrator
to create the helper. This prevents the documented bootstrap from recreating the
same PUBLIC-executable function.

Confirmed follow-up: existing authenticated policies on catalog/BOM tables and
`agent_write_log` are broad. The task transition function also accepts actor and
force parameters without validating the caller in its body. Anonymous access is
now closed, but signed-in RBAC/actor enforcement needs its own reviewed change
and compatibility tests. Do not describe this containment as complete tenant,
ownership, or role isolation.

The Performance Advisor was also run: it reported existing index/RLS optimization
findings (18 unindexed FKs, 18 auth init-plan warnings, one missing primary key,
34 unused indexes, 150 multiple-policy findings, eight duplicate indexes).
No performance schema changes were made.

## Recovery guidance

For any access regression, fix the legitimate server/session/role path first.
Do not disable RLS, restore anonymous table grants, or reopen arbitrary-SQL RPCs.
The migration retains all records and server privileges, so administrators can
inspect the backup without weakening the client boundary.

Reference: [Supabase RLS disabled in public remediation](https://supabase.com/docs/guides/database/database-linter?lint=0013_rls_disabled_in_public).
